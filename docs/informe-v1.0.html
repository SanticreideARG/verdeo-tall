1 · Resumen Ejecutivo

Verdeo es la empresa argentina de comida saludable por suscripción que entrega menús semanales a domicilio en cuatro regiones del país. Este informe documenta el cierre del primer long run de desarrollo: la construcción, desde cero, de la plataforma interna que centraliza ventas, conversaciones, cocina, logística y analítica del negocio.

Qué es Verdeo (la plataforma)

Verdeo es un sistema de gestión comercial y logística de tipo panel único. Reemplaza el flujo disperso de planillas, chats sueltos y mensajes manuales por una herramienta integral donde el equipo opera el ciclo completo del negocio: desde que un cliente escribe por WhatsApp, Messenger o Instagram, hasta que su pedido se cocina, se rutea y se entrega. Incorpora además una capa de inteligencia artificial (Claude y Ollama) para asistencia interna y, a futuro, respuesta automatizada de conversaciones.

Qué se construyó en este sprint

Una aplicación web completa sobre el stack TALL (Tailwind + Alpine.js + Laravel + Livewire), desplegada en una infraestructura Docker de nueve contenedores sobre Windows 11 con WSL2. La aplicación cubre 19 áreas funcionales con control de acceso por rol, doble base de datos (entorno de prueba y producción), temas visuales claros y oscuros, y portal diferenciado para clientes finales.

Estado general

El sistema es plenamente operativo en entorno local para la gestión interna: todo el flujo de órdenes, cocina, clientes, zonas, menús, estadísticas y configuración funciona de extremo a extremo. La capa de mensajería entrante/saliente (webhooks de Meta, despacho real de WhatsApp y automatizaciones de n8n) se encuentra construida a nivel de interfaz pero aún no conectada a los proveedores externos. Esto, junto con el endurecimiento para producción (HTTPS, contraseñas, modo debug), constituye el grueso del trabajo pendiente.

Lectura rápida: el motor de gestión interna está terminado y probado con datos sembrados. Lo que falta es principalmente integración externa y preparación de producción, no funcionalidad nueva de negocio.

2 · Bitácora por Jornada

A continuación se reconstruye el recorrido del sprint a partir de los registros de sesión y el contexto disponible. Las fechas de las jornadas tempranas son aproximadas: se reconstruyen del historial del proyecto y no de marcas de tiempo exactas. Las jornadas finales (18 al 20 de mayo) están documentadas con precisión.

Nota de honestidad documental: la línea de tiempo de la fase inicial es una reconstrucción a partir del contexto del proyecto, no un registro literal. Se presenta agrupada por jornadas de trabajo lógicas más que por días calendario exactos.

Jornada 1 — Infraestructura
Cimientos: Docker, WSL2 y el stack base

Montaje de la infraestructura completa: nueve contenedores Docker sobre Windows 11 + WSL2 Ubuntu 22.04. Se resolvieron varios problemas propios del entorno: el bug del data-root de Docker Desktop, MySQL 8 sobre sistema de archivos NTFS (deshabilitando SSL y la autogeneración de llaves RSA), y el conflicto del puerto 80 con el Apache de WSL —motivo por el cual nginx quedó en el puerto 8888. Se inicializó el proyecto Laravel 10 con Livewire 4.3 (Volt SFCs), Tailwind v3 y Alpine.js.

Jornada 2 — Autenticación y esqueleto
Login, roles y navegación

Construcción del sistema de autenticación con cinco roles (Administrador, Responsable de Zona, Colaborador, Cocina, Cliente). Login con fondo de campo de estrellas animado, logo y tema oscuro. Navegación adaptativa por rol: sidebar completo para Admin y Responsable, dock móvil glassmorphic para Colaborador y Cliente, vista exclusiva de cocina para el rol Cocina. Registro de invitados en /unirme.

Jornada 3 — Modelos de datos y dominio
Zonas, productos, menús y órdenes

Definición del modelo de datos del negocio: User, Conversacion, Producto, Plato, Orden y OrdenItem. CRUD de zonas geográficas con menús semanales en JSON. CRUD de productos con cinco tipos de menú, platos por día y doble precio (250g y 400g). Flujo completo de órdenes con su máquina de estados.

Jornada 4 — Operación diaria
Conversaciones, cocina y logística

Inbox multicanal unificado (WhatsApp + Messenger + Instagram) con filtros y detalle por conversación. Vista de cocina con autorefresco cada 10 segundos, alerta sonora y banner verde para pedidos nuevos. Módulo de entregas con mapa interactivo, marcadores GPS, geocodificación desde dirección y hoja de ruta imprimible.

Jornada 5 — Inteligencia y analítica
Asistente IA, estadísticas y CRM

Asistente IA multi-turno con selector de proveedor (Claude / Ollama) y prompt en español rioplatense. Panel de estadísticas con KPIs comparados contra el período anterior, ventas por zona, top de productos y embudo de conversión. CRM de clientes con segmentación (frecuentes, en riesgo, nuevos). Integración de la OllamaService con el modelo local llama3.2.

Jornada 6 — Configuración y pulido
Ajustes, marketing, temas y portal del cliente

Panel de Ajustes integral: apariencia (5 temas), IA, WhatsApp por zona, API de WhatsApp (Evolution o Meta), canales Messenger/Instagram, servidor de datos (Alice/Betty) y sincronización. Módulos de marketing por canal. Portal del cliente con sus propias órdenes. Rastreador de enlaces cortos. Log de actividad. Pulido visual general.

18 – 20 de mayo de 2026 — Cierre del sprint
Datos de prueba, documentación, branding y correo

Jornada final del long run, documentada en detalle:

  • Datos de prueba multicanal: se ejecutó el TestConversacionesMulticanalSeeder, cargando 24 conversaciones de prueba (12 WhatsApp + 6 Messenger + 6 Instagram) vía docker exec en el contenedor verdeo_laravel.
  • Reescritura de la página de Ayuda: se reemplazó la escueta guía de 5 secciones por un acordeón "Funcionalidades" de 19 secciones que cubre cada área del sistema. La pestaña "Acerca de" se actualizó a v0.2.0, sumando MySQL 8, Redis y Claude API al detalle de stack.
  • Integración del logo: el logo original (diseño circular de hoja tropical, 1024×1024, 1,6 MB) se optimizó a 256×256 PNG de 62 KB mediante PHP GD dentro del contenedor —una reducción del 96 %—. Se generaron favicons de 32 px y 192 px y se añadieron las etiquetas <link> en ambos layouts, con cache-buster ?v=2 para invalidar el 404 cacheado.
  • Configuración de correo en Ajustes: nueva tarjeta "Correo electrónico" con cuatro presets de proveedor (SMTP / Gmail / Outlook / Resend), autocompletado de host y puerto, contraseña segura de escritura única, campos de remitente y prueba de conectividad TCP vía fsockopen.
  • Datos estadísticos: el EstadisticasTestSeeder insertó 142 órdenes repartidas en 30 días con fechas históricas reales. El sistema quedó con 168 órdenes totales, $7,5 M de facturación (entregadas), distribución realista por zona y tendencia creciente en los últimos 7 días.

4.4 · Patrones clave

Volt SFCs

Los componentes Livewire se escriben como archivos únicos (Volt). Las rutas Volt no son cacheables: nunca debe ejecutarse route:cache.

Doble base de datos

Alice (prueba) y Betty (producción) se alternan desde Ajustes. Sincronización en un paso de zonas, productos y platos de Alice → Betty.

Redis como backend único

Caché, sesiones y colas comparten Redis. Horizon supervisa los workers de cola.

Credenciales de escritura única

API keys, contraseñas SMTP y tokens se guardan en Setting: se escriben pero nunca se devuelven; la UI muestra ●●●● si hay valor.

4.5 · Servicios de IA

  • Ollama — modelo local llama3.2 (3.2B, Q4_K_M, ~2 GB). Inferencia solo CPU: 60–90 s por respuesta, ~4,2 GB de RAM al cargar. Servicio app/Services/OllamaService.php con métodos generate(), chat(), stream(), classify(), extractOrderFromText(), suggestReply(), isAvailable().
  • Claude (Anthropic) — proveedor cloud configurable desde Ajustes para el chatbot y el asistente interno.

5 · Asuntos Pendientes

El backlog se organiza por prioridad. Lo crítico bloquea la puesta en producción; lo alto habilita la mensajería real; lo medio activa la automatización; lo bajo son mejoras deseables.

Crítico   Bloquea producción

Modo debug habilitado. APP_DEBUG debe deshabilitarse antes de exponer el sistema; hoy filtra trazas internas.

Sin HTTPS. No hay certificados SSL ni configuración HTTPS en nginx. Es requisito para webhooks de Meta y para tráfico de clientes.

Crash loop de Evolution API. El contenedor verdeo_evolution lleva semanas en Restarting(1): Prisma intenta migrar sobre una base no vacía. Solución: hacer baseline de las migraciones de Prisma.

Contraseñas de desarrollo. Todas las credenciales (DB, n8n, Evolution, admin) son de desarrollo y deben endurecerse antes de producción.

6 · Análisis de Tiempo y Proyección

6.1 · Qué llevó más tiempo de lo esperado

  • La infraestructura, no el código. El mayor desgaste del sprint estuvo en el entorno: el bug del data-root de Docker Desktop, MySQL 8 negándose a arrancar sobre NTFS, el conflicto del puerto 80 con Apache. Cada uno consumió tiempo de diagnóstico desproporcionado frente a su tamaño real.
  • Los stubs de Volt. El conflicto entre los stubs ⚡*.blade.php generados por make:livewire y los SFCs reales generó fallos intermitentes y difíciles de rastrear hasta identificar el patrón.
  • El crash loop de Evolution API. Sigue sin resolverse; se degradó a baja prioridad porque no bloquea la gestión interna.
  • Archivos Blade complejos. El quoting de PHP, Blade y directivas en la shell obligó a escribir los archivos vía scripts intermedios, sumando fricción.

6.2 · Qué resultó eficiente

  • Volt SFCs. Una vez resuelto el tema de los stubs, los componentes de archivo único aceleraron mucho la construcción de pantallas.
  • El patrón de credenciales reutilizable. El mismo patrón de Setting de escritura única sirvió para API keys, tokens y la nueva contraseña SMTP sin rediseño.
  • Datos sembrados. Los seeders permitieron validar estadísticas, CRM y el inbox con volúmenes realistas sin esperar datos reales.
  • El sistema de temas. Basado en variables CSS, sumar temas nuevos fue casi gratuito.

6.4 · Cuándo podría llegar a producción

Para un lanzamiento mínimo viable —gestión interna real, sin automatización de IA— alcanza con el endurecimiento de producción y HTTPS: estimado en 2 a 3 jornadas de trabajo enfocado. El sistema ya soporta el ciclo completo de órdenes, cocina y logística.

Para el lanzamiento completo con mensajería real bidireccional y automatización de WhatsApp vía n8n, el horizonte es de 8 a 12 jornadas adicionales, condicionado a resolver el crash loop de Evolution API y a la configuración de las cuentas de Meta.

Recomendación: separar el lanzamiento en dos etapas. Primero la gestión interna (rápida, alto valor inmediato para el equipo); después la capa de mensajería automatizada, que depende de integraciones externas con sus propios tiempos.
